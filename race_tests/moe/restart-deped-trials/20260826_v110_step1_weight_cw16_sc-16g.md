# v110 Step1 Gate/Up `coalesced_width=16`（sc-16g）

## 结论

该方向在 source/codegen gate 被关闭，不创建编号版本，不改动 `dorm` 性能源码，也不生成 `restart-submission`。

v110 的 Step1 Gate/Up global-to-shared copy 受 swizzled shared layout 约束，每线程物理向量宽度为 8 个 FP16。把这些 copy 的 `coalesced_width` 从编译器默认值提高到 16 后，LayoutInference 明确拒绝：

```text
Fatal: Vector size 8 is not divisible by coalesced width 16
```

因此这不是“编译成功但性能未知”的候选，而是当前公开 TileLang copy/layout 表达下不可表示的 32-byte/thread 搬运。

- 目标：尝试让每线程一次请求 16 个连续 FP16，减少源级搬运请求和地址指令
- 合规性：仅公开 TileLang primitive；无 async copy、foreign source、注入或额外 import

## 验证

1. OJ 静态结构检查：PASS。
2. 公开 `T.ldg256` 的最小 float32 global-to-global 往返：C500 上 PASS，证明 32-byte value 本身能由公开 DSL 表达。
3. v110 Step1 候选 Case3 编译：FAIL，停止于 LayoutInference，尚未生成设备 C++/ISA。
4. 搜索公开 DSL：存在 `T.ldg256`/`T.stg256`，但后者仅是 global store；没有对应的公开 256-bit shared-store primitive。
5. 历史交叉检查：此前 Step2 的 `T.ldg256` 直接 vector-to-swizzled-shared 同样被 LayoutInference 拒绝；手工 local/unpack 版本曾出现高半物化错误或三 Case 7.9%–11.1% 回退。

由于 source/codegen gate 未通过，没有执行 correctness、AB/BA 或 mcProfiler。对编译失败候选计时没有意义。

## 性能含义

v110 的普通 Step1 `T.copy` 已由目标 layout 固定为 8×FP16（128 bit）每线程的合法向量宽度。仅提高 `coalesced_width` 不能把它变成 16×FP16；要做到这一点必须同时改变线程到 swizzled shared 的物理映射，或使用当前公开 DSL 没有提供的 256-bit shared store。手工拆包会增加标量化、地址与类型转换，历史证据已经显示其动态代价大于静态 load-site 收益。
