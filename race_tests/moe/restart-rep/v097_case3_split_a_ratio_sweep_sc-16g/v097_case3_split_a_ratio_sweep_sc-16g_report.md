# v097 Case3 split-A ratio sweep 报告

## 1. 上版本遗留问题

v095 的 64/64 split-A 已改善 Case3 Step1，但二分点来自自然对半，并非硬件证据证明的最优点。本轮检查早发请求量与 fragment 生命周期是否还有更好平衡。

## 2. 问题原因分析

已验证：完整 A-before-Gate0 不如 64/64 split，64/64 又显著优于更晚发 A 的旧路径，说明 Step1 对同步 A 请求时序敏感。当前假设是二分比例改变 Gate0 计算期间的在途请求数和后半 fragment 生命周期。

## 3. 本版本解决方案

保持 v095 其余路径不变，比较 `32 rows -> Gate0 -> 96 rows` 与 `96 rows -> Gate0 -> 32 rows`。预期至少一个比例相对 v095 Case3 改善 1.2%。

## 4. 具体落地策略

- `v097_split32_functional.py`：early/late 为 32/96。
- `v097_split96_incorrect.py`：early/late 为 96/32。
- odd 和 next-even 两个 producer 同步修改。
- 只使用 `T.Parallel`、普通 shared 写和既有同步路径；无 async/foreign code。

## 5. Benchmark 对比

MetaX C500 `sc-16g`，Case3，同进程 AB/BA，3 rounds，W20/R30，完整 padded-output correctness。

| 版本 | Case3 时间/变化 | correctness | 结论 |
|---|---:|---|---|
| v095 64/64 | parent，约 7.83–7.85 ms | PASS | 开发性能基线 |
| 32/96 | paired median `+1.738860%` | PASS | 3/3 变慢，拒绝 |
| 96/32 | 未计时 | FAIL，8.7% mismatch | correctness gate 否决 |

32/96 三轮变化：`[+1.738860, +1.691237, +1.868391]%`，pstdev `0.074855%`。

## 6. Profile / codegen 指标

| 指标 | v095 64/64 | 32/96 | 96/32 |
|---|---:|---:|---:|
| Step1 MT | 226 | 226 | 220 |
| Step1 ST | 54 | 52 | 56 |
| waves/PEU | 2 | 2 | 2 |
| generated bytes | 30283 | 30113 | 30255 |
| generated SHA | `d627d221...` | `6455e8f6...` | `9573030c...` |

两个比例都真实改变了 lowering。32/96 即使 ST 略降仍明显变慢，说明 Gate0 前仅 32 行不能维持足够请求覆盖。96/32 虽 MT 降低，但数值错误，资源数字没有性能意义。因 screen 已明确否证，未采集 mcTracer/mcProfiler/Roofline。

## 7. 实验总结

单纯移动二分点失败。64/64 仍是当前可靠比例：向 32 方向会减少过多 early requests，向 96 方向触发不可靠的 `T.Parallel(96, ...)` lowering/写入行为。下一步不继续细扫比例，而尝试四个 32-row chunk 与 Gate0、Gate1、Up0、Up1 producer 交错，以同时避免 32/96 的后半突发和 96/32 的非标准映射。
